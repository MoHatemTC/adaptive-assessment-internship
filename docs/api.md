# The API

Written for someone building the frontend, who is not in this repository.

Machine-readable specs are committed beside this file — `docs/api/openapi-*.json`, one per
service, regenerated by `python scripts/dump_openapi.py` and checked for drift by the test
suite. This page is the part a spec cannot tell you: which calls to make in which order,
and why some things are deliberately not in the response.

| service | port | you talk to it |
|---|---|---|
| **assessment-orchestrator** | 8080 | yes — this is the API |
| **live-voice** | 8765 | yes, for spoken answers |
| bank-registry | 8081 | only to register a bank |
| grader | 8082 | no |
| competency-graph | 8083 | no |

The orchestrator proxies `GET /banks`, so a candidate-facing frontend needs exactly one
base URL. CORS is open and non-credentialed; narrow it with `CORS_ALLOW_ORIGINS`.

---

## The candidate flow

```
POST /assessments                    -> session_id, presenting
   |
   +--> presenting.item             render by modality
   |
POST /assessments/{id}/responses     -> presenting (the next one), or report
   |
   '--> repeat until stop == true
```

Every lifecycle call returns the **same shape**, so there is one thing to render and one
place to look for "what now": `presenting` when there is a question, `report` when there
is not.

### Begin

```http
POST /assessments
{
  "bank_id": "AIE",              // omit for the deployment's active bank
  "target_variables": null,      // omit to assess every competency the bank measures
  "intake": {"C1": 3},           // self-rating 1-5, seeds a narrower prior
  "confidence": {"C1": true},    // is that rating trusted? untrusted seeds a wide prior
  "use_llm": true
}
```

`201` with the first question. The `bank_id` and the bank **version** are pinned to the
session from here on — you never send them again, and a bank replaced mid-session cannot
change the pool underneath the candidate.

Do not send `seed` in production. It exists for deterministic replay; omitting it draws OS
entropy, and exposure control must not be predictable.

### Render

`presenting.item.modality` decides what to draw. The fields that matter per modality:

| modality | fields |
|---|---|
| `mcq` | `stem`, `options` |
| `code` | `prompt`, `language`, `function_name`, `starter_code` |
| `open` / `voice` | `question`, `answer_format`, `spoken` |

`spoken` is how you tell a voice item from a typed one without inspecting anything.
`starter_code` may be a deliberately incomplete scaffold — that is authored, not a bug.

### Answer

```http
POST /assessments/{id}/responses
{"type": "mcq",   "chosen_index": 2}
{"type": "code",  "code": "def solve(x): ..."}
{"type": "voice", "transcript": "..."}
```

Or `multipart/form-data` with an `audio` file for a spoken answer; it is transcribed
server-side.

`type` must match the modality currently presented — a mismatch is a `422` rather than a
silently mis-graded answer.

The response carries `last_graded`, which is an **acknowledgement, not a result**:

```json
{"item_id": "...", "modality": "mcq", "accepted": true, "flags": []}
```

No score, no correctness, no detail. That is not squeamishness — feedback after each answer
changes what the assessment measures. A candidate told which hidden test failed learns
something between question four and question five, and the estimate that comes out is of a
person who was being taught mid-measurement.

`flags` carries exactly one class of thing: infrastructure. `SANDBOX_UNAVAILABLE` or
`PACKAGE_INFRASTRUCTURE_ERROR` mean their answer moved no estimate and they may be asked
again. Show that. It is the one thing they are entitled to know while answering.

### Finish

When `stop` is true, `report` is populated.

**Report the band RANGE, not the point band.** At the standard-error target,
within-one-level accuracy runs about 99% while exact-band accuracy runs about 65%. A UI
that renders `level: 3` alone is asserting a confidence the measurement does not support;
render `credible_interval_95` or the neighbouring levels with it.

`decision_status` is `provisional` for every measured competency and will stay that way
until external exact-band calibration passes. It is not a placeholder — do not render it as
a certified result.

## Errors

One shape everywhere:

```json
{"detail": "the presented item changed while this request waited", "code": "stale_answer"}
```

`detail` is for a person. `code` is for your `if`. The ones worth handling:

| code | status | what to do |
|---|---|---|
| `stale_answer` | 409 | a double-submit; re-read the session and render what it shows |
| `answer_type_mismatch` | 422 | a client bug — the wrong modality was submitted |
| `answer_missing` / `answer_invalid` | 422 | show the message, let them answer again |
| `grader_unavailable` | 503 | nothing was recorded; the same item can be retried |
| `capacity_reached` | 503 | no new session right now; existing ones are unaffected |
| `assessment_unknown` | 404 | the session expired or was never created |

Capacity fails **closed**: at the limit a new assessment is refused rather than an
in-progress one being evicted.

## Spoken answers

Two ways, and the second is better where you can use it.

**Typed transcript.** Send `transcript` and you are done.

**A real interview.** `live-voice` runs the realtime bridge:

```
POST  :8765/api/live/rooms       {item_id, question, assessment_session_id}
WS    :8765/ws/live/{room_id}    candidate PCM up, interviewer PCM down
GET   :8765/api/live/rooms/{id}  status, turns, and the finished transcript
```

Or embed `:8765/interview` in an iframe and let it drive the socket. It ships its own audio
worklet, so it must be served from that origin.

Pass `assessment_session_id` so the interview trace groups with the rest of the session.
The room produces a transcript; you then submit it as a normal answer. **The room does not
grade** — that separation is why an audio failure can be reported as an audio failure
rather than as a candidate who said nothing.

## Registering a bank

`bank-registry` accepts one from another service. Items and graph go together: a bank
without its graph pairs with nothing, and the coverage gate then asks a graph authored for
a different bank what a competency requires — which marks every required node unmeasured
and vetoes convergence for the rest of the session.

```http
POST :8081/banks
{
  "bank_id": "MY-BANK",
  "title": "...",
  "items": [{
      "item_id": "q1",
      "modality": "mcq",
      "measures": [{"variable": "C1.2", "weight": 1.0}],
      "cat": {"a": 1.4, "b": -0.2, "c": 0.25},
      "payload": {"stem": "...", "options": ["..."], "answer_index": 1}
  }],
  "graph": {"nodes": [...], "edges": [{"from": "C1.2", "to": "C1", "relation": "CONTRIBUTES_TO"}]}
}
```

`POST /banks/validate` runs every check and writes nothing — use it from an authoring tool.
Findings name the item, node or competency at fault.

`POST` refuses an id that exists, including a checked-in one. `PUT /banks/{id}` replaces and
creates a new version; sessions already running keep the version they began with.
`DELETE /banks/{id}` removes a posted bank, and a checked-in one of the same id reappears
underneath it.

The graph uses `from`/`to` — exactly the JSON a bank author would otherwise check in.

### What gets refused

Errors, all of which would otherwise surface as an unexplainable assessment:

- item parameters out of range — `a` above 3.0 does not rank oddly, it ranks meaninglessly
- duplicate item ids, or no active item at all
- a graph that pairs with a different bank
- a measured variable with no node — invisible to coverage and to blocking
- a required node no active item measures — an unsatisfiable gate
- more required nodes than the question budget can cover — the gate could never be
  satisfied and every session would end on the budget escape, reporting a stop it never
  chose

Warnings never block. A bank with no graph is legal; the coverage gate simply does not run.

**There is no authentication on this endpoint.** See `docs/operations.md`. Set
`ADMIN_API_ENABLED=false` on any deployment that does not need the write path.

## The author view

`GET /assessments/{id}/diagnostics` and `/state`, both refused unless
`AUTHOR_DIAGNOSTICS_ENABLED`.

They carry the posterior, the shortlist, the criterion phase and which item the engine would
have picked — enough to reverse-engineer difficulty, and enough for a candidate to tell how
they are doing while still being measured. **Never expose them on a candidate-facing
deployment.** They exist so an assessment author can see why an item was chosen; without
them, an assessment nobody can audit mid-flight.
